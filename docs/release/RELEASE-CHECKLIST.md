# Release checklist

Reproducible, in order. Every box is checked by a concrete command; the
commands are the checklist. Run from the repository root.

## Release model

The repository contains **source code and release tooling only** —
generated release artifacts are never committed:

- source code, docs, and `scripts/` stay in Git;
- release artifacts (binaries, SHA256SUMS, installer copies) are
  generated by `scripts/release.ps1` into `dist/`, which is gitignored —
  locally for verification, by CI for publication;
- publishing is **tag-driven**: pushing a `vX.Y.Z` tag triggers the
  release workflow (`.github/workflows/release.yml`), which validates
  the tag against the workspace version, builds the release binaries on
  both platforms (the Linux build is the static musl binary — ADR-V0-1's
  distribution story), smoke-tests each artifact, assembles the bundle
  with `SHA256SUMS` and the installers, and publishes the release;
- ordinary pushes and pull requests never publish anything; the
  workflow never commits, pushes, or moves tags;
- `dist/` is throwaway build output — deleting it loses nothing that
  cannot be regenerated by the release script.

The checklist below treats `dist/` as generated, untracked output at
every step. The repository is hosted at github.com/bloopdex/vaultline
(public, default branch master, hosted 2026-09-07): pushes run the CI
gates and v* tag pushes run this checklist's publishing half.

## 1. Version consistency

- [ ] `Cargo.toml` `version` (the workspace, single-sourced) matches
      the release version.
- [ ] `CHANGELOG.md` has an entry for the release version with the date.
- [ ] `vaultline version` output makes sense: binary version = release
      version; state schema v1; engine restic.

```powershell
cargo run --quiet -- version
cargo run --quiet -- version --json
```

## 2. Full validation before the tag

- [ ] All gates green: format, clippy with warnings denied, the
      workspace test suite, supply-chain verification, license checks,
      the workflow self-validation, the benchmark regression check, and
      the diff check.

```powershell
cargo fmt --all --check
cargo clippy --all-targets -- -D warnings
cargo test --workspace
cargo vet check --store-path supply-chain
cargo deny check
python scripts/check-workflows.py
python scripts/bench-check.py
git diff --check
```

## 3. Local release bundle (Windows)

- [ ] `scripts/release.ps1` completes: the tree was clean, the release
      build succeeded, `dist/` holds the checksummed binary, and the
      artifact smoke (version + template round trip) passed.

```powershell
powershell -File scripts/release.ps1
```

- [ ] The reported version in the bundle matches the release version.

## 4. Tag and publish

- [ ] The annotated tag `vX.Y.Z` is created on the bump commit; the tag
      and the workspace version are identical (the workflow enforces it).

```powershell
git tag -a v0.9.0 -m "vaultline 0.9.0"
```

- [ ] Push the tag; the tag's own CI run and the release workflow both
      complete green.
- [ ] The published release carries the two binaries, `SHA256SUMS`, and
      both installers.

## 5. Independent verification of the published artifact

- [ ] Download the release binary on a machine that did not build it;
      verify the checksum against the published `SHA256SUMS`.
- [ ] `vaultline version` on the downloaded binary reports the release
      version; `init` + `validate` complete.

## 6. After the release

- [ ] The repository tree is clean (dist/ is ignored, never committed).
- [ ] The state of record matches: the versioned surfaces, the SOT
      Section 8 row, and the changelog entry all name the release
      version.
